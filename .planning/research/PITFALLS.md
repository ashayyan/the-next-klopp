# Pitfalls Research

**Domain:** Interactive, visual-first football (soccer) learning web app, built by AI agents over months, for one ADHD learner on Windows (localhost first, Vercel for phone viewing), Premier League as reference league.
**Researched:** 2026-11-27
**Confidence:** MEDIUM overall. Verified this session against official or primary pages: PL SCR/SSR rules, Vercel Deployment Protection scopes, StatsBomb attribution text, FBref/Opta removal (news reports). Not verified this session (marked LOW or "verify at phase time"): Transfermarkt/Understat/Capology/Wyscout ToS text, FIFA RSTP and agent-regulation current state, DuckDB-WASM exact bundle size, StatsBomb open-data PL coverage details, kloppy coordinate defaults for the pinned version. Licensing notes are risk flags, not legal advice.

Phase labels used below (map to real roadmap phase numbers when the roadmap exists):
**Setup** (toolchain, repo, CI), **Research** (Phase 0 sprint), **Design** (directions, DESIGN.md, Pitch Standard), **Platform** (app shell, content-as-data, local state, deploy), **Pipeline** (Python data), **Golden** (golden lesson), **M1** (Track 0, Track 1, Watch Gym L1), **Every phase** (recurring gate).

## Critical Pitfalls

### Pitfall 1: Watch Gym has no legal video supply

**What goes wrong:** Milestone 1 promises "10-30 s clips, one question each, answered on a pitch overlay." Broadcast PL footage cannot be downloaded or stored (out of scope per PROJECT.md), YouTube embeds cannot be trimmed to exact frames with a custom pitch overlay drawn on top reliably (and overlaying on the embedded player is a ToS risk), and official highlights rights are not yours to cut. Agents then quietly download clips "for testing" or build an overlay UI on iframes that breaks.
**Why it happens:** The feature is specified at the UX level; nobody checks the content supply chain. The most ADHD-critical feature (the learner cannot watch matches) is the one with the weakest legal path.
**How to avoid:** Decide the clip strategy in the Research phase, before building the player. Recommended: (a) primary = animated reconstructions rendered on the canonical pitch from open event/tracking data (StatsBomb 360 freeze frames, Metrica, SkillCorner open, DFL/Sportec open); (b) secondary = "bring your own clip": learner picks a local file via a file input, nothing uploaded or stored; (c) tertiary = plain YouTube embed with a link-out question (no overlay), start/end params only. Write the decision to `docs/decisions/`. Label reconstructions honestly as "reconstruction from data, not broadcast".
**Warning signs:** Any `.mp4` in the repo or `public/`; a lesson spec with `video: "clip-*.mp4"`; a yt-dlp or ffmpeg call in an agent plan; overlay code positioned `absolute` over an iframe.
**Phase to address:** Research (decision), Design (clip + overlay component spec), M1 (build).

### Pitfall 2: "Premier League everywhere" collides with what free data actually covers

**What goes wrong:** Lessons promise PL examples with tracking data, 360 freeze frames, pitch control, or modern pressing metrics. Open tracking datasets (Metrica sample games, SkillCorner open A-League, DFL/Sportec Bundesliga, PFF World Cup) contain no PL matches. StatsBomb 360 is limited to selected tournaments and competitions. StatsBomb open PL coverage is, as far as known, the 2015/16 season (plus a small Arsenal 2003/04 set); older seasons often lack event types or qualifiers present in modern data (check per competition: pressure events, freeze frames). Agents then fabricate "PL pressing numbers" or silently substitute another league.
**Why it happens:** The "PL default" rule is a design principle; data availability is an engineering fact discovered late.
**How to avoid:** In the Research phase, build a one-page **data coverage matrix** (provider x competition x season x data type: events, 360, tracking, lineups) generated by script from `competitions.json` and each dataset's docs, not from memory. Every lesson spec declares its dataset; a validator rejects a lesson whose claim text says "Premier League" but whose data ref is another league unless it carries a visible "Why not PL: ..." label. Use PL for rules, finance, history, structure; use the best-fitting open dataset for tracking/pressing and say so.
**Warning signs:** A lesson title with "PL" plus "pitch control" or "tracking"; a data ref to a file nobody has opened; "illustrative numbers" in a chart.
**Phase to address:** Research (matrix), Pipeline (validator), every content phase.

### Pitfall 3: Hallucinated facts, stats and regulation details in agent-written lessons

**What goes wrong:** Sonnet-class writers produce fluent, confident text with wrong numbers (a player's xG per 90, a rule's threshold, a transfer fee, the year a law changed). A same-family "verifier" re-reads from memory and agrees (correlated error). The registry fills with plausible URLs that do not exist or do not say what is claimed.
**Why it happens:** Verification is specified as "a different agent", but not as "an agent that fetches the cited source text and compares". Link checking (Haiku) only proves a URL resolves.
**How to avoid:** (1) **No bare numbers in prose.** Numeric facts in MDX must be a component bound to a pipeline output or to a registry entry with page/section reference, for example `<Fact id="pl-scr-green" />`; a lint fails on unannotated digits in prose. (2) Verifier works from fetched/archived source excerpts stored in the registry (retrieval date, quoted <= 25 words, section), not from model memory. (3) Registry entries need: URL, retrieved-on date, archived copy or snapshot URL, license, and the exact claim it supports. (4) Link checker also compares a keyword/claim anchor against page text. (5) Opus verifier for metrics, regulations and finance, per brief, but give it the fetched text.
**Warning signs:** Verifier reports pass in under a minute with no fetch calls; two lessons give different values for the same fact; registry URLs all at the same domain depth patterns; sources with no retrieval date.
**Phase to address:** Research (registry schema), Platform (lint + `<Fact>` component), every phase (gate).

### Pitfall 4: Regulation facts that are stale or wrong the day they ship

**What goes wrong:** Concrete examples verified this session: the PL Squad Cost Ratio cap is **85%** of football revenue plus net player-trading result (with a 30% allowance giving a Red Threshold of 115% at the start); the **70%** figure is UEFA's. SCR replaces PSR from 2026/27, but 2025/26 ran PSR with SCR in shadow form, and levies only apply to breaches from 2027/28. SSR adds working-capital (GBP 12.5m), liquidity and Positive Equity tests (90% / 85% / 80% by season). The PL's own page labels the GBP 85m stress-test figure "proposed". An agent mixing these (70 vs 85, PSR 105m rolling loss vs SCR single-season) teaches the wrong system. Same class of risk: FIFA RSTP and the FIFA agent regulations (fee caps, legal challenges, edits), PL homegrown/work-permit (GBE) rules, EPPP categories, Saudi Pro League foreign-player and salary rules, IFAB Laws (new edition every 1 July).
**Why it happens:** Rules change seasonally, sources disagree (press summaries vs the Handbook), and models recall older regimes (PSR) more strongly than new ones.
**How to avoid:** Regulation facts live in one `regulations.json` (value, source, effective-from, status: in force / transitional / proposed, last-verified date), rendered through `<Rule id=... />` with a visible "as of <date>, source" stamp. Primary source only (PL Handbook appendices, IFAB Laws PDF, FIFA legal documents); press is secondary. A scheduled (quarterly, plus each 1 July and 1 September) re-verify task is part of the roadmap. Mark proposed/transitional values as such. Teach PSR as history and SCR as current, side by side, with both dates.
**Warning signs:** A regulation number without a date stamp; "PSR" described in present tense; a source that is a news site when the Handbook exists; no "last verified" field.
**Phase to address:** Research (domains 15, 20), Platform (`<Rule>` component), every regulation lesson, quarterly maintenance.

### Pitfall 5: Source licensing and ToS: "free to read" treated as "free to reuse"

**What goes wrong:** (a) **FBref lost Opta advanced data (xG, progressive passing, etc.) on 2026-01-20** after Opta ended the arrangement; any pipeline, lesson or `soccerdata`/`worldfootballR` code path relying on FBref advanced stats is dead or stale. The brief's seed list may still reference it. (b) Transfermarkt, Understat and Capology have scraping-restrictive ToS (not verified this session; most stats sites forbid scraping and block it). Community datasets derived from scraping (for example a CC0-labelled transfermarkt dataset) carry a license label that does not clean the upstream rights. Capology salaries are estimates. (c) StatsBomb open data: README asks you to credit StatsBomb as the data source and use their logo whenever you publish or share analysis based on it; a LICENSE/user agreement is linked from the repo. (d) The learner's own Wyscout/Opta/StatsBomb licensed data: usually non-redistributable, including derived figures shown on a deployed site. (e) The Wyscout public research dataset (Pappalardo et al.) is a different thing from commercial Wyscout and has its own citation terms; do not conflate them. (f) PL Handbook, IFAB Laws and books are copyrighted: paraphrase and link.
**Why it happens:** Agents optimise for "data I can reach", and registries record `free: true` without distinguishing read/scrape/redistribute/derive.
**How to avoid:** Registry gets four separate license fields: `read`, `automated_access`, `redistribute`, `derivative_ok`, plus `attribution_text`. Pipeline may only auto-download sources where `automated_access` is explicitly yes (StatsBomb open, Metrica, SkillCorner open, DFL, kloppy-supported open sets, Companies House under OGL). Everything else is "read, summarise in own words, link". Attribution component renders the StatsBomb credit and logo automatically on every page that uses their data (CI check). Local-licensed data is **lab-only**: it runs on the learner's PC, is excluded from Vercel builds by path, and no figure derived from it is rendered in deployed lessons. Remove FBref advanced stats from every plan; record the date in the registry as a removed source.
**Warning signs:** `requests.get("https://www.transfermarkt...")` in the pipeline; a lesson chart without attribution; registry `free: true` with no license text; Wyscout files anywhere under the repo root.
**Phase to address:** Research (registry schema, per-source ToS read), Pipeline (allow-list), Platform (attribution component, Vercel ignore rules).

### Pitfall 6: Licensed or large data enters git history (and cannot be removed)

**What goes wrong:** One agent run copies a sample of the learner's Wyscout/event data into `pipeline/tests/fixtures` or `public/data`, or commits a 200 MB parquet. A private GitHub repo is still a redistribution to a third party (GitHub) and Vercel builds deploy from it; the blob persists in history after deletion, bloating the repo and requiring history rewrite.
**Why it happens:** `.gitignore` is added after the first data touch; tests want realistic fixtures; YOLO mode auto-approves commits.
**How to avoid:** First commit includes `.gitignore` (`/data/raw`, `/data/local`, `*.parquet` outside an allow-listed `/data/derived` path, `.env`, `/feedback`), `.gitattributes`, a pre-commit + CI check that fails on files > 1 MB or on paths in a deny list, and gitleaks for secrets. Test fixtures are synthetic or tiny slices of open data with a README citing license. Data location for the learner's local files is an env var (`LOCAL_DATA_DIR`) outside the repo (for example `E:\football-local\`), never inside it.
**Warning signs:** `git status` shows `data/`; repo > 50 MB; `git lfs` suggested to "fix" it; a fixture with real player names from a licensed provider.
**Phase to address:** Setup (before any pipeline code).

### Pitfall 7: Vercel Deployment Protection looks on but leaves content reachable

**What goes wrong:** Verified this session: **Standard Protection protects preview and generated deployment URLs but leaves the production custom domain public**; "All Deployments" scope also covers production. Docs and changelog disagree on plan availability and on whether generated production URLs are covered for new projects. Other leaks: protection-bypass tokens or "shareable links" pasted into PRs/README; Playwright E2E against previews using a bypass secret committed to the repo; licensed or personal files in `public/` (including `/feedback` notes, `/research` dumps) served even if "protected" later changes; source maps exposing content.
**Why it happens:** The setting has several scopes with confusing names; learner clicks the default.
**How to avoid:** Choose the strictest scope that the learner's plan allows (All Deployments / Vercel Authentication on production too) and **prove it**: after each deploy-config change, `curl -I` the production URL and a preview URL without a session and expect 401/redirect to auth; put this in a documented smoke script run at each milestone. Bypass secrets only in GitHub Actions secrets, never in the repo. Build only `/content` and derived small data; `research/`, `feedback/`, `data/` are excluded from the Vercel root via `.vercelignore`. Treat "no secret data in bundle" as the real control, since protection can be misconfigured: assume the deployed bundle may become public and ship nothing that would hurt.
**Warning signs:** A production URL that opens in a private window; `bypass` tokens in any file; `.vercel.app` URLs in public places; `public/` containing JSON larger than lesson needs.
**Phase to address:** Platform (deploy), re-check each milestone.

### Pitfall 8: Coordinate-system and direction-of-play bugs across providers

**What goes wrong:** Providers differ in units, origin, axis direction and attacking-direction normalisation: StatsBomb events use a 120 x 80 grid (y increases downward from the top); Opta is 0-100 percent with origin bottom-left; Wyscout is 0-100 percent with y downward; Metrica is 0-1 normalised; SkillCorner/DFL tracking use metres centred on the pitch. Direction of play flips at half-time or per team. Mapping 120 x 80 onto a 105 x 68 pitch distorts distances (xG-by-distance, pass length). A y-flip produces left/right mirrored tactics (left-back shown on the right) which is a factual error in a learning product, and bugs are invisible without known reference points.
**Why it happens:** Each component author converts locally; kloppy's defaults (normalised coordinates, assumed pitch dimensions when real ones are unknown) are not read for the pinned version.
**How to avoid:** One canonical pitch module in meters (105 x 68 default, configurable) and one coordinate-converter package, with **property and golden tests**: for every provider, penalty spot, both goal posts, 6-yard box corners, halfway circle centre, corner flags map to the same canonical points; round-trip tests; left/right asymmetry test (a known left-footed shot or a known player's side). Components accept only canonical coordinates. Record in `docs/decisions/` whether kloppy conversion or own converters are used, and the pitch-dimension assumptions per provider. Distance-based metrics state they use approximate dimensions when real ones are unknown.
**Warning signs:** Raw provider coordinates inside any component; "flipY" boolean props; SVG viewBox with a non-105:68 aspect ratio; a pass map where the goal appears on the wrong end.
**Phase to address:** Design (Pitch Standard), Pipeline (converters + tests).

### Pitfall 9: Metrics implemented "close enough" and silently disagreeing with published values

**What goes wrong:** Own-built xG, xT, VAEP or PPDA gives numbers that differ from references, and lessons then contradict the sources the learner reads elsewhere. Typical divergences: xG is model-specific (StatsBomb xG vs Opta vs Understat differ per shot; teach as model output, not truth); PPDA definitions differ by provider (which actions count as defensive, which pitch zone, whether it is by opposition passes in the attacking 60% of the pitch, StatsBomb pressure-based variants); xT depends on grid size (the common 16 x 12), iteration count and how move-vs-shot probabilities are estimated; VAEP depends on SPADL conversion, number of previous actions, and the model; SPADL conversion from different providers is not identical.
**Why it happens:** "Checked against known values" is in the brief but no reference values are chosen up front; an agent writes the test from its own output.
**How to avoid:** At Pipeline planning, pick 3-5 reference values per metric from published sources (paper tables, library test fixtures, provider-reported numbers for the same match) and store them in `tests/reference_values.json` with source and definition. A metric function must state its definition in a docstring and in the lesson ("Our PPDA: ..."). Where the library already implements it (socceraction, mplsoccer, kloppy), wrap it and pin versions rather than reimplement; use a bespoke implementation only when a lesson needs to expose the maths, and test it against the library. Differences versus published values are documented, not hidden.
**Warning signs:** A test that asserts the function's own output; a metric with no `definition` field; two lessons using different PPDA zones.
**Phase to address:** Research (domain 12/15 reference values), Pipeline, then each metric lesson.

### Pitfall 10: Progress and feedback are split across devices or silently fail on Vercel

**What goes wrong:** IndexedDB/localStorage on the PC (localhost) and on the phone (Vercel) are separate stores, so the learner has two diverging progress states, and mobile browsers can evict script-writable storage. The "I'm confused here" button is specified to write a local feedback file the build agents read: browsers cannot write files, a Next.js API route writing to disk works on localhost but fails (read-only filesystem) on Vercel, so on the phone, confusion notes vanish while the UI says "saved". Also: the dev server is the only place the feedback file path exists; a schema change in progress storage without migration wipes months of mastery data.
**Why it happens:** "Local-first" and "view on phone" are both required, and their interaction is not designed.
**How to avoid:** Decide explicitly and record: **PC localhost is the system of record**; the phone deployment is read-mostly (lessons work, progress is stored locally on that device and clearly labelled "this device only") with manual JSON export/import as the bridge, plus `navigator.storage.persist()` request. Feedback: write to an IndexedDB queue everywhere; on localhost a dev-only route drains the queue to `/feedback/*.jsonl` (git-ignored); on Vercel, show an honest "saved on this device; export to send" and an export button. Versioned DB schema with tested migrations and an automatic JSON backup download prompt before any migration. Test: delete-and-restore from export is an E2E test.
**Warning signs:** `fs.writeFile` in an app route; a success toast without a persistence check; no `version` field in the export JSON; no migration test.
**Phase to address:** Platform (local state design), re-verified at every schema change.

### Pitfall 11: Shipped chapters break because shared pieces change under them

**What goes wrong:** The rolling release promises "never break a shipped chapter," but a new lesson needs a changed `Pitch` prop, a re-versioned pipeline output (numbers change), a new design token, a bumped library, or a content-schema change, and old lessons regress. Visual and E2E tests miss it because they only cover each lesson's happy path or because visual baselines drift.
**Why it happens:** Components and data outputs are shared and unversioned; "reviewed PR" does not catch semantic changes.
**How to avoid:** (1) Lesson spec pins `data` refs to a versioned dataset ID (content hash or `v2026.11`); the pipeline writes new versions side by side instead of overwriting; a lesson updates only by an explicit PR. (2) Component API changes are additive; breaking changes need a new component name or a codemod plus run of all shipped lessons. (3) A `content:validate` command checks every lesson spec against the current schema and every component prop. (4) One E2E per shipped lesson stepping through every screen, plus pixel snapshots of key states. (5) Run the full shipped-lesson suite in CI on every PR that touches `/components`, `/pipeline` or tokens, not only on content PRs.
**Warning signs:** Pipeline PR that changes numbers in many lessons; component PR with no list of affected lessons; E2E that only opens the first screen.
**Phase to address:** Platform (versioning, validator), Pipeline (versioned outputs), enforced every phase.

### Pitfall 12: Research sprint that never converges (and delays the learner for months)

**What goes wrong:** Brief section 6.2 lists 22+ domains with many sub-domains; each spawns sub-agents that produce long findings, source lists and visual ideas. Synthesis cannot absorb it, the concept map keeps growing, "one more domain" delays DESIGN.md and Milestone 1, and the learner (who needs to start studying and rebuilding match-watching) waits. Raw dumps also pollute agent memory (explicitly not wanted per PROJECT.md).
**Why it happens:** Research is cheap to start, has no natural stop, and every finding feels useful. The brief locks "no content before research approved" without a depth cap.
**How to avoid:** Time- and size-box each domain: output cap (for example 1500 words findings, 15 registry entries minimum 5 high-quality, 10 visual ideas), stop rule "two consecutive searches add no new source or concept". Split research into **Wave 1 (everything needed for Track 0, Track 1, Watch Gym L1, DESIGN.md, concept-map skeleton)** and **just-in-time research per later track, run in the discuss/plan step of that track**. The learner checkpoint approves the concept map and the curriculum skeleton, not 22 research folders. Log deferred domains in `GAPS.md` with an explicit "researched before Track N" tag. Use Fable only per the escalation protocol, never to "finish" research.
**Warning signs:** Research phase > 2-3 weeks of calendar time; findings files > 3000 words; concept map nodes > 300 before any lesson exists; synthesis agent output truncated or generic.
**Phase to address:** Research (scoping), roadmap structure.

### Pitfall 13: Over-building components and platform before a lesson needs them

**What goes wrong:** The brief's component catalogue (section 9.5) is large (tactics board, pitch control, transfer simulator, formation builder, timeline scrubber, etc.). Agents, given months and parallel waves, build a "design system" of 30+ components with Storybook-like pages while zero lessons exist, then the golden lesson needs three of them and they do not fit.
**Why it happens:** Components are measurable output; lessons need content decisions. The brief says components are built "just before the first lesson that needs them" but phases can drift.
**How to avoid:** Roadmap rule: no component without a named consuming lesson spec in the same or next plan; catalogue entries are "reserved names" until then. Cap Milestone 0 to the pitch renderer, a handful of primitives (step container, glossary card, predict-reveal, drag-token, scrubber) and the golden lesson. Review at each phase: components with zero consumers are deleted or frozen.
**Warning signs:** `/components` count rising while `/content` is empty; demo/playground routes; "reusable" in a plan without a second consumer.
**Phase to address:** Design, Platform, Golden.

### Pitfall 14: AI-slop design that passes the checklist

**What goes wrong:** The app ends up with default Inter-plus-gradient look, rounded-card grids, glassmorphism, emoji bullets, stock-looking green striped pitches, charts with default D3/Recharts palettes, and tooltip-heavy dashboards: the exact things the brief bans. Agents satisfy the written anti-slop list literally while still looking generic, and review screenshots at 3 widths by the same agent rubber-stamp it.
**Why it happens:** Rules are negative ("no gradients") not positive (a defined visual identity); design review uses the same model that produced the design.
**How to avoid:** The design-direction checkpoint must render 2-3 directions with **real content** (one tactics, one data lesson, three widths) and the learner chooses. Then encode the choice as tokens enforced by lint (no raw hex or px outside tokens, banned class lists, allowed fonts), a written "Pitch Standard" with reference renders, and a **golden-lesson reference** that other lessons are compared against in review. Colour-blind-safe palettes checked by a simulator, not by eye. Design review prompt includes the reference screenshots and asks for concrete defects, run by a fresh agent with the design-taste skill.
**Warning signs:** Same card component repeated 6 times in a grid; hero with a gradient; icons from one default set used decoratively; pitch with alternating mown stripes by default; chart legends away from the data.
**Phase to address:** Design, Golden, review gate in every UI phase.

### Pitfall 15: Text walls creep back despite the 60-words rule

**What goes wrong:** The limit is checked per screen manually. Agents split one wall into five screens of 58 words each (fragmentation, no interaction), or put the text in tooltips, captions and glossary cards that are counted nowhere. Lessons become click-through slideshows: "See it" and "Touch it" steps that do not require a decision. Quiz variants by a cheap model produce ambiguous distractors and recognition-only questions.
**Why it happens:** The measurable rule (words) gets optimised; the actual goal (generative interaction, retrieval) is not measured.
**How to avoid:** Validator counts all visible strings per screen including captions and aria-visible hints; fails > 60 words; also checks each lesson has >= 1 step type that blocks progress until the learner acts (drag, predict, place, compute), at least one prediction made **before** reveal, and retrieval items that require recall or construction, not only multiple choice. Retrieval items have a rationale and, for contested or visual answers, accepted alternatives. Haiku-written variants are reviewed in a batch against a rubric before entering the queue. Golden lesson screen-time target measured with a stopwatch test.
**Warning signs:** Lessons with > 12 screens; no interaction in the first three screens; every quiz is 4-option MCQ; learner time per screen under 5 seconds.
**Phase to address:** Platform (validator), Golden, every lesson.

### Pitfall 16: Gamification and review mechanics that backfire for ADHD

**What goes wrong:** Even "honest" mechanics become dark patterns: mastery rings that decay or turn red work as hidden streaks; a review queue count badge is a guilt counter; confetti and sounds on every step become noise and reward-seeking; "days learned this month" displayed against a goal feels like a streak; variable-ratio rewards pull towards novelty-chasing instead of understanding; the SR queue after two weeks off shows 300 cards. Also hyperfocus rabbit holes (endless glossary links) and novelty-seeking (asking agents for new tracks instead of finishing one).
**Why it happens:** Standard gamification templates are copied; "no streaks" is implemented literally but the mechanism is reintroduced under another name.
**How to avoid:** A written "Honest mechanics" list in DESIGN.md with forbidden patterns: no decay, no red for overdue, no counters of "due" beyond a capped "up to N today", no loss framing, no comparisons, no push notifications, rewards only on mastery events and never random. Use an established scheduler (FSRS via `ts-fsrs`, or Anki-style SM-2 variant) rather than hand-rolled; on return after a gap, reschedule quietly and show at most a small fixed batch. Low-energy mode: one-tap session with defined content source and a fixed end; counts as a day. Motion respects `prefers-reduced-motion` and has an in-app calm setting; no autoplay loops. Glossary cards are shallow (one level) with a "back to where I was" anchor. Learner can pause any lesson with a resume checkpoint.
**Warning signs:** Any red number; "streak", "don't break", "overdue", "behind" in strings (add a content lint for these words); review count > cap; animations running without user action.
**Phase to address:** Design (mechanics list), Platform (SR + low-energy + welcome-back), Golden.

### Pitfall 17: Windows-specific breakage

**What goes wrong:** Concrete, likely in this project:
- **Spaces in the project path** (`E:\To become new klop`): unquoted paths in npm scripts, Python tools and native-module builds fail intermittently.
- **`make data`** does not exist on Windows by default; agents write a Makefile that only works in WSL or Git Bash.
- npm scripts using `VAR=value cmd` or `&&` chains and Unix tools (`rm`, `cp`, `grep`) break in cmd/PowerShell.
- **CRLF vs LF**: shell scripts, MDX and JSON hashed for content versions differ between Windows and CI Linux; `bash\r` errors.
- **Case-insensitive filesystem**: `import Pitch from './pitch'` works on Windows and fails on Linux CI and Vercel builds.
- Playwright **screenshot baselines generated on Windows differ from Ubuntu CI** (fonts, anti-aliasing), so visual tests fail only in CI.
- `python` resolves to the Microsoft Store stub; Python 3.13/3.14 may lack wheels for pinned scientific packages.
- Long paths in `node_modules` and git; symlink creation needs privileges (already hit once: the taste skill symlink).
- Antivirus or sync tools slow file watching.
**Why it happens:** Agents default to Linux/macOS idioms; the learner's machine is the only Windows environment, and CI is Linux.
**How to avoid:** Record in `docs/decisions/`: task runner is `npm run <script>` (Node scripts or `just`/`uv run` for Python, with `cross-env`, `shx` or plain Node scripts) and **no Makefile as the primary interface**; `.gitattributes` with `* text=auto eol=lf`; `core.longpaths=true`; `.python-version` and `uv` for pinned Python (3.11 or 3.12) and a lockfile; a CI matrix with `windows-latest` for the smoke path (install, `npm run dev` boot, `npm run data` on fixtures) and `ubuntu-latest` for full tests; ESLint rule for import-path case (`import/no-unresolved` with case-sensitive check) ; generate Playwright baselines only in the CI container (or the official Playwright Docker image) and label them `-linux`; quote all paths; consider moving the working copy to a no-space path (decision for the learner at the Setup checkpoint). Test `git clone` + fresh setup on a clean path as a setup acceptance step.
**Warning signs:** "works in Git Bash only"; baseline PNGs updated by a local run; a Makefile with `export` or `$(shell ...)`; CI green only on Linux job.
**Phase to address:** Setup.

### Pitfall 18: Heavy in-browser runtimes (Pyodide, DuckDB-WASM, WebGL) wreck load time, especially on the phone

**What goes wrong:** Pyodide first load is roughly 6-7 MB of runtime plus several seconds of init (about 4-5 s reported), and numpy/pandas add several more MB, then import time of seconds; scientific stack libraries used by the pipeline (mplsoccer needing matplotlib, socceraction, kloppy with its dependencies) may not be available as Pyodide-compatible wheels. DuckDB-WASM bundles are tens of MB uncompressed (verify the pinned version). Loading either in the app shell, or per lesson page, makes every lesson slow and can crash iOS Safari under memory pressure. SVG with thousands of event points or 22 animated players at high frame rate stutters on a phone; WebGL pitch control on mobile may fail.
**Why it happens:** The stack is chosen for capability before a load budget exists.
**How to avoid:** Set a **load budget** now (for example: lesson shell JS <= 200 KB gzip, first interactive <= 2 s on a mid phone; any page needing a heavy runtime shows an explicit "Load Python lab (about X MB)" button and caches via service worker). Do not use DuckDB-WASM for ordinary lesson data: precompute small JSON (or small Parquet read lazily) in the pipeline; reserve DuckDB-WASM for a dedicated SQL lab lesson. Run Pyodide in a Web Worker, create it once per session, and keep exercises to small pandas/numpy tasks; heavy compute stays in the pipeline. Use Canvas for > ~2000 marks; SVG for pitch + <= ~50 elements; WebGL only for pitch-control surfaces with a static-image fallback. Add Lighthouse or bundle-size checks to CI (`size-limit`).
**Warning signs:** A route importing `@duckdb/duckdb-wasm` at the top level; Pyodide loaded in `_app`/layout; Largest asset > 1 MB in the shell; CPU throttled test dropping below 30 fps.
**Phase to address:** Platform (budget, loading pattern), Pipeline (precompute), Python-lab and tactics-board phases.

### Pitfall 19: Agent workflow drift over months (decisions lost, memory polluted, YOLO side effects)

**What goes wrong:** Context resets across months; agents re-decide settled questions or reintroduce banned patterns; `docs/decisions/` is written but not read at plan time; agentmemory fills with research dumps (explicitly forbidden); YOLO/auto mode merges plans without a human checking a PR; the learner's feedback files are not read before planning; skills (taste-skill, K-Dense, skills.sh) from third parties are installed without reading them (including promotional or telemetry skills such as `offer-k-dense-web`), or via symlinks that break GSD checks. Research sub-agents with web access and shell rights are exposed to **prompt injection** from fetched pages.
**Why it happens:** Long horizon, many agents, high autonomy, little friction.
**How to avoid:** Every plan's context includes a fixed **"constitution" file** (PROJECT.md core value + rules + the decision index) and the plan checker greps for violations (data in git, `.mp4`, banned words, bare numbers). Decision records have a one-line index file that agents must read. agentmemory holds only learner profile, project rules and decision pointers (allow-list of memory types). Install skills project-locally, pin versions, read each `SKILL.md` once and record it in `docs/SETUP.md`. Research agents: no write access outside `research/`, no access to `.env` or tokens, summaries only returned, treat fetched text as data (see untrusted-input boundary). Keep the human checkpoints from the brief and add one: merge of anything touching deployment, data policy or the pipeline allow-list needs the learner or an explicit review.
**Warning signs:** Same question answered two ways in different phases; memory entries over a few KB; `.env` or token paths read in agent transcripts; PRs merged with zero review comments.
**Phase to address:** Setup, then every phase.

### Pitfall 20: Contested football knowledge presented as settled

**What goes wrong:** Tactical terms (half-space, false 9, inverted full-back, press triggers, "low block") are used with different definitions by different coaches and authors; "never assume vocabulary" produces glossary entries that pick one definition silently. Analytics claims presented as fact (xG predictiveness, ACWR injury prediction, PPDA as pressing intensity, "possession wins matches", market-value models). Scouting/role labels from the learner's own model imported as ground truth.
**Why it happens:** An LLM gives a single authoritative-sounding definition; the brief requires "contested" labels but gives no mechanism.
**How to avoid:** Registry flag `contested: true` with two or more cited positions; `<Contested>` component renders both sides; glossary entries carry "as used here" definition and a source, with "other usage" where known. Watch Gym questions with subjective answers (pressing triggers, "was this a good decision") store the rationale, a source or expert view, and accepted alternatives; "eye improving" metric only from questions with defensible ground truth (for example event-data labelled outcomes) and not mixed with opinion items.
**Warning signs:** Glossary definition with no source; a quiz answer disputed by the learner's "confused" note; the word "always" or "never" in tactical copy.
**Phase to address:** Research (domains 8-14), Platform (components), every tactics lesson.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Hard-coded numbers in lesson prose | Faster writing | Unverifiable, stale, un-reproducible; verifier cannot trace | Never (use `<Fact>`/`<Stat>`) |
| Overwriting pipeline outputs in place | Simple pipeline | Changes numbers in shipped lessons silently | Never after first shipped lesson |
| Raw provider coordinates in components | One less converter | Mirrored/stretched tactics, hard to fix later | Never |
| Copy-pasting a component per lesson | Fast first lesson | N diverging copies, breaks "never break shipped chapters" | Only in the golden-lesson prototype, then refactor |
| `localStorage` for progress | Trivial | Size limits, no migration story, easy loss | Prototype only; use IndexedDB with versioned schema before the learner studies |
| Playwright baselines from the Windows machine | Quick snapshots | Fails in Linux CI, tempts disabling visual tests | Never as CI truth |
| Makefile as the only data entry point | Matches brief wording | Not runnable natively on Windows | Only as thin wrapper over `npm run data` |
| Skipping unit tests for "simple" metrics | Speed | Wrong numbers taught as truth | Never for xG/xT/VAEP/PPDA |
| Hand-rolled spaced repetition | No dependency | Bad schedules, backlog bugs | Never (use FSRS/ts-fsrs) |
| Lesson-level inline styles | Quick tweak | Defeats token enforcement, slop returns | Never |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| StatsBomb open data | No attribution; assuming 360 and PL coverage; bulk-downloading everything | Credit StatsBomb with logo wherever shown; read `competitions.json` to see coverage; download only the slices lessons use; pin a commit of the open-data repo |
| FBref / soccerdata / worldfootballR | Using FBref advanced stats (removed 2026-01-20) | Drop it; use StatsBomb open for events/xG, official sources for tables; record removal in registry |
| Transfermarkt / Understat / Capology | Scraping in the pipeline; treating estimates as facts | Read-and-link only, unless a documented permitted API/dataset license; label values "estimate, source, date" |
| kloppy | Trusting default coordinates/pitch size; mixing versions | Pin version; set coordinate system and pitch dimensions explicitly; test converters against reference points |
| socceraction/SPADL | Assuming identical SPADL across providers | Per-provider conversion tests; note differences in lessons |
| mplsoccer/matplotlib | Using for web visuals | Use only in pipeline for static reference renders; web visuals use the canonical SVG/Canvas pitch |
| Companies House accounts | Manually transcribing figures | Store source filing ID + page; check Open Government Licence terms; date-stamp |
| PL Handbook, IFAB Laws PDFs | Quoting long passages; citing press summaries | Paraphrase, link to the official PDF with version/date; regulation JSON with last-verified |
| YouTube embeds | Overlaying UI on the iframe; downloading clips | Embed as-is with link-out questions; overlays only on reconstructions |
| Vercel | Default protection scope; bypass tokens in repo; deploy `/research` | See Pitfall 7; `.vercelignore`; secrets in CI only |
| GitHub Actions | Linux-only CI; visual baselines from Windows | Windows smoke job + Linux full job; baselines from CI container |
| Playwright | Tests that only load the page | Step through each screen, assert interaction effects, include reduced-motion run |
| agentmemory / skills.sh skills | Storing research dumps; unreviewed third-party skills | Allow-list memory types; read and pin each skill; install project-locally |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Loading Pyodide/DuckDB-WASM eagerly | Slow first paint, phone crashes | Lazy, worker-based, explicit load button, service-worker cache | First time a heavy runtime lands in a shared layout |
| Whole-season event JSON in the client | Multi-second parse, jank | Precompute per-lesson slices; Parquet/JSON chunks by match | Event files in the tens of MB per lesson |
| SVG for thousands of marks | Low fps, laggy drag | Canvas above about 2000 marks; aggregate (hexbin/binning) | A full-season shot map or heatmap |
| Animating 22 players plus overlays with React state per frame | Dropped frames | Imperative rAF loop outside React state, transforms only, `will-change` sparingly | Tracking replay at 25 Hz on a phone |
| MDX compile in the request path | Slow dev reload | Compile at build; cache; keep MDX small, logic in components | Dozens of lessons |
| Unversioned large data in Vercel build | Slow deploys, size limits, accidental exposure | Ship only derived small data; `.vercelignore` | Once data folder exceeds tens of MB |
| Playwright suite grows linearly with lessons | CI takes an hour | Parallel shards, run only affected lessons on content PRs, full suite nightly and on shared-component PRs | 40+ lessons |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Prompt injection via fetched web pages into agents with shell access (YOLO mode) | Token/`.env` exfiltration, malicious commits | Sandbox research agents, no secrets on disk, deny network egress for execution agents, summaries only |
| Secrets in repo or logs (`gh` token, Vercel token, bypass secret) | Account compromise | `.env.example` only, gitleaks pre-commit and CI, secrets only in GitHub/Vercel settings |
| Learner's confusion notes and notes DB deployed | Personal data public | Git-ignore `/feedback`, exclude from Vercel root, keep progress client-side |
| Third-party skills with network or telemetry behaviour | Data leakage, promo injection | Read SKILL.md, pin, disable promotional skills (`offer-k-dense-web`), project-local install |
| Vercel production domain left public (Standard Protection) | Learner data/content exposed | Strictest scope, `curl` smoke test, ship nothing sensitive |
| Learner's licensed data exposed through derived charts on Vercel | Licence breach | Lab-only local mode; build-time check that no lesson data ref points to `LOCAL_DATA_DIR` |
| Dependency supply chain (npm/PyPI) via agent-added packages | Malicious or abandoned deps | Lockfiles, `npm audit`/`pip-audit` in CI, new dependency requires a decision record line |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| Long placement diagnostic | Fatigue on day one; ADHD abandonment | 5-8 minute adaptive diagnostic with a skip-and-return; results are suggestions; test basics, ask once about specialist courses |
| Welcome-back screen that lists what was missed | Shame, avoidance | One warm recap, one easy first step, nothing about days missed |
| Glossary cards that stack | Disorientation, rabbit holes | One level, always a "back to the lesson" anchor |
| Everything animates | Overstimulation, distraction | Motion only where it carries meaning; reduce-motion mode; focus mode removes chrome |
| Predict step that is just a button | Illusion of learning | Prediction must be an input (place, drag, draw, number) committed before reveal |
| Time estimates that are wrong | Lost trust | Measure real durations in the golden lesson; calibrate from local logs |
| "I'm confused" button needs a form | Never used | One tap saves location; optional note; auto-capture screen id and step |
| Phone and PC show different progress | Confusion, distrust | Label the device-local store; export/import; see Pitfall 10 |
| Colour-only distinction on pitches (red vs green teams) | Colour-blind inaccessible | Shape/pattern plus colour; check with simulator; legend always visible |
| Watching exercises start long | Attention drop | Start at 10-30 s with one question; learner chooses to extend |

## "Looks Done But Isn't" Checklist

- [ ] **Lesson:** Often missing a real prediction input and a retrieval item that requires recall; verify by tracing the blocking steps in the spec.
- [ ] **Numbers in a lesson:** Often hand-typed; verify each ties to a `<Fact>`/`<Stat>` and a registry entry with a retrieval date.
- [ ] **Regulation lesson:** Often missing "as of" date, effective-from date and primary source; verify against the Handbook/official page, not press.
- [ ] **Pitch visual:** Often drawn with raw provider coordinates or wrong direction of play; verify with the reference-point test and a left/right asymmetry check.
- [ ] **Attribution:** Often missing on pages using StatsBomb data; verify the logo and credit render on every route with a StatsBomb data ref (CI check).
- [ ] **Deployment:** Often "protected" only on previews; verify with `curl -I` against production and a preview from outside the account.
- [ ] **Data pipeline on Windows:** Often tested only in Git Bash; verify `npm run data` from PowerShell on a clean clone in a path with a space.
- [ ] **Local state:** Often no migration or export test; verify delete-IndexedDB-and-restore E2E.
- [ ] **Confusion button:** Often fails silently on Vercel; verify on the phone deployment.
- [ ] **Accessibility:** Often keyboard path missing for drag interactions; verify every drag has a keyboard alternative and works with reduced motion on.
- [ ] **Role coverage tags:** Often applied by Haiku with no review; verify the coverage matrix at the milestone, not per lesson only.
- [ ] **Low-energy mode:** Often a link to a normal lesson; verify it ends by itself in 3-5 minutes and counts as a day.
- [ ] **Golden lesson:** Often polished once then not reused as a reference; verify later lessons are screenshot-compared to it.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Licensed data committed to git | HIGH | Stop pushes; rewrite history (`git filter-repo`), force-push, rotate anything exposed, check Vercel deployments for copies, delete GitHub caches/forks, document incident |
| Vercel production exposed | MEDIUM | Switch scope to All Deployments, redeploy, rotate bypass tokens, audit bundle contents, delete old deployments |
| Wrong regulation taught | LOW-MEDIUM | Fix `regulations.json`, regenerate, bump lesson version, note correction in "What's new" |
| Metric disagrees with published value | MEDIUM | Add reference test, fix or document the definition, rerun pipeline into a new versioned output, update affected lessons by PR |
| Coordinate bug found late | HIGH | Fix converter, add golden tests, rebuild all derived data into a new version, re-run all lesson E2E and visual checks |
| Progress lost by schema change | HIGH | Restore from last export; add migration and mandatory export prompt; this is why backup-before-migrate is required |
| Research sprint overrun | MEDIUM | Freeze domains, ship concept-map skeleton from what exists, move the rest to just-in-time tags in `GAPS.md` |
| Component sprawl | MEDIUM | Delete consumer-less components, keep names reserved in the catalogue |
| Slop identified after many lessons | HIGH | Fix tokens and base templates first so lessons inherit; re-review golden lesson; batch regenerate screenshots |
| Windows-only breakage in CI | LOW | Add Windows smoke job, normalise line endings (`git add --renormalize .`), fix import casing |
