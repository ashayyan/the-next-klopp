**As a** learner, **I want to** have lessons authored as validated data that render in a navigable app protected on Vercel, **so that** every shipped lesson is traceable, tested, never public and never broken.

<objective>
Build the validator that every lesson ships through: one parse with the build's own MDX parser, one step extractor, one word counter shared with `review:screens`, the generated lesson manifest, and the structural and safety rules, each proven by a failing fixture with its exact message.

Implements CONTEXT "Form of the validator" (`scripts/validate-content.ts`, pure rules in `scripts/lib/content/`, `npm run validate`, pre-commit and the `test` CI job, one line per break), "plus structural rules: schema, MDX↔spec step parity", "How does the walker discover lessons?" (the validator generates the manifest), post-research decisions "Lessons carry no frontmatter … rule `mdx-frontmatter`", "Lesson MDX may not contain export, import or {expression} … rule `mdx-code`; block components … rule `block-component`", "Validator runs in the test CI job", "a shared countWords is used by validator and review". RESEARCH Patterns 2 and 8 conventions, Pitfalls 1, 2, 4.

Planner decisions: rule `unknown-component` (a JSX name outside the provider list) and `step-heading` (each step opens with exactly one `##`) are structural rules added here so a lesson that would throw at render time cannot ship; `link-scheme` implements RESEARCH threat T-05-04. Messages for rules without UI-SPEC copy follow its template "what broke. how to fix it." and are fixed in this plan.

Purpose: CONT-02 has a single, tested enforcement point before any content exists to break it.
Output: validator core and CLI, manifest, eight rules with fixtures, hook and CI wiring.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| lesson MDX to compiled JavaScript | MDX is code; anything the parser accepts runs in the learner's browser |
| lesson links to the browser | authored URLs become clickable anchors |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-03 | Tampering / Elevation | lesson MDX | high | mitigate | `mdx-code` rejects ESM, flow and text expressions and every expression attribute except a statically evaluated literal `sides`; `unknown-component` limits elements to the provider list; both run in pre-commit and the required `test` job |
| T-05-04 | Tampering | links in lessons | medium | mitigate | `link-scheme` allows only `https:` and root-relative paths; chips use registry URLs only (05-09) |
| T-05-18 | Repudiation | pre-commit bypass (`--no-verify`) | low | accept | the same validator runs in the required `test` CI job, so a bypassed hook cannot merge |
| T-05-12 | Tampering | ci.yml run steps | medium | mitigate | the new step has no GitHub expression; baselines-guard.test.ts enforces it |
| T-05-SC | Tampering | npm installs | high | accept | no package installed here (05-01 installed `@mdx-js/mdx`) |
