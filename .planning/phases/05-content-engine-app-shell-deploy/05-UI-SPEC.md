# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**What this contract covers.** Phase 5 has these UI surfaces, and nothing else:

1. The app shell: the app bar, home (one obvious next action), `/tracks`, `/tracks/:trackId`, `/tracks/:trackId/:chapterId`, `/whats-new`, the not-found and error screens, and the "coming next" state of unshipped tracks.
2. The lesson runtime frame at `/learn/:lessonId`: lesson header, Lesson Loop step rail, step region (heading and at most 60 words), visual and interaction slot with the "Text version" fallback switch, source line, and Back / Next navigation, plus the lesson-complete view.
3. The claim components `<Fact>`, `<Stat>`, `<Rule>` (effective and as-of dates) and `<Contested>` (two or more sourced sides), their visible source chip and the source popover that shows the registry entry; and `<Num>`.
4. Three new registered interactions for the fixture lesson and the walker: `quiz-choice`, `predict-then-reveal`, `order-sequence`; plus the registry wrappers of the Phase 3 interactions (`scene-playback`, `drag-player`, `converter-probe`).
5. The dev-only lesson status badge and "Drafts visible" marker.
6. Copy for the validator, the frozen-ID check and the protection smoke script (terminal output read by a non-programmer).

Out of scope (Phase 6): focus mode, "I'm confused here", glossary cards in lessons, progress, mastery rings, review queue, low-energy mode. No screen in this phase shows a progress number, a streak, a score or a completion count.

**This contract conforms to `docs/DESIGN.md`; it does not reinvent it.** Every token, size, colour and motion value below is quoted from DESIGN.md section 3 (floodlit, ADR 0010). Where DESIGN.md already fixes a rule, this file names it and adds only what Phase 5 needs on top.

**Sources used:** `05-CONTEXT.md` (locked decisions, all chosen as the recommended option under learner delegation), `REQUIREMENTS.md` (CONT-01..06, PLAT-02..04, QA-01, QA-03..05), `ROADMAP.md` Phase 5, `STATE.md`, `docs/DESIGN.md` sections 1-8, `docs/decisions/0010-visual-direction.md`, `04-UI-SPEC.md`, `04-UI-REVIEW.md`, the code in `src/ui/**`, `src/routes/**`, `src/pitch/**`, `src/scene/**`, `scripts/review/**`, `schemas/source.schema.json`, `research/SOURCE_REGISTRY.json` (218 entries), `research/concept-map.json`, `scripts/research/lib/domains.ts` (the 29 track titles), `research/formations/findings.md` (contested points), and the skills `design-taste-frontend` and `frontend-design` (cliché list: no middle-dot meta strings outside the DESIGN.md date line, no labels above headings, no mono for labels, no arrow suffixes, numbered markers only for real sequences).

**Autonomous run.** The learner delegated every choice. No question was asked. Every open point below is marked **Decided** with the reason, so the planner can treat it as locked. The repo is public: this file holds no personal detail about the learner.

## Spacing Scale

Declared values (multiples of 4), from DESIGN.md section 3.3 (`--space-*`):

| Token | Value | Usage in Phase 5 |
|-------|-------|------------------|
| xs | 4px | Icon to label; chip to the word before it; chip inner padding (inline); context line to `h1` |
| sm | 8px | Between controls in one group (Back and the screen count; Move up and Move down); list row vertical padding; gap between quiz options |
| md | 16px | Page padding below 768 px; panel padding at 375; gap between regions at 375; gap between list rows' text lines and their status |
| lg | 24px | Page padding 768-1023 px; panel padding from 768 px; gap between regions at 768 and inside the 1440 columns; body to CTA |
| xl | 32px | Page padding from 1024 px; column gap at 1440; gap between What's new entries; gap between the two track groups |
| 2xl | 48px | Gap between the app bar and the page header from 1024 px |
| 3xl | 64px | Bottom page padding from 1024 px |

Grid (DESIGN.md 3.3): 4 columns / 16 px gutter at 375, 8 columns / 24 px gutter at 768, 12 columns / 32 px gutter at 1440, content at most 1280 px wide; the lesson stage may run to 1440 with 32 px padding.

Exceptions:
- **Touch targets:** every control outside running text is at least 44 × 44 px and at least 8 px from the next (`tap-size`). This includes list rows, nav links, Back, Move up / Move down and the "Text version" switch.
- **Source chip (inline target):** the chip sits inside a sentence, so it uses the WCAG 2.5.8 inline exception that `tap-size` already implements (a `display: inline` or `inline-block` button inside a `<p>` with words around it). Size: at least 24 × 24 px (`min-h-6 min-w-6`), horizontal padding 4 px. It is the only target in this phase below 44 px.
- **Borders and rules are not spacing:** list rules and `--border-rule` are 1 px; the current nav link underline is 2 px; the error panel's left border is 4 px (DESIGN.md 3.1); the focus ring is at least 2 px.
- **Pitch geometry** stays in screen pixels and metres (DESIGN.md section 4); nothing changes in Phase 5.

## Typography

Exactly the DESIGN.md section 3.2 scale: four sizes, two weights.

| Role | Size | Weight | Line Height | Phase 5 use |
|------|------|--------|-------------|-------------|
| Label | 14px | 400 (600 for the selected or current value, and for the chip numeral) | 1.4 | Nav links, breadcrumb, context lines, list meta lines, badges, screen count, source line, source chip, popover rows, "Text version", quiz helper and inline errors |
| Body | 16px | 400 (600 for list-row titles and the quiz question) | 1.5 | Step body (at most 60 words), home summary, What's new summary, rule card text, Contested sides, quiz options, feedback text |
| Heading | 24px | 600 | 1.25 | Step heading (`h2`), list group headings (`h2` "Ready to study", "Coming next"), What's new entry titles (`h2`), status panel headings, "Lesson finished" |
| Display | 36px | 600 | 1.1 | The one `h1` of every page (lesson title, track title, "Tracks", "What’s new", home's next-lesson title) and `<Stat variant="figure">` figures |

- **Families:** Display and Heading use `--font-display` (Mona Sans at 125 %); Body and Label use `--font-sans` (Mona Sans at 100 %); numbers use `--font-mono` (Geist Mono) with `tabular-nums`.
- **Mono only for numbers that change or align:** `<Stat>` values (inline and figure), time readouts inside interactions, and numeric table columns. Never for labels, chip numerals, track numbers, dates, ids or headings.
- **Measure:** body text runs at most 65ch (45-70 characters per line) on every page.
- **Lengths that keep the scale honest** (enforced by the lesson schema and the registry props schemas):
  - Lesson title: at most 40 characters (it is the `h1` and sits inside "Start: {title}").
  - Step heading: at most 8 words. It counts toward the 60 words of its step.
  - Quiz question: at most 25 words; each option at most 12 words; 2 to 4 options.
  - Quiz explanation, reveal text: at most 30 words each.
  - Order-sequence items: 3 to 6 items, each at most 10 words.
- **Copy typography:** curly quotes (“ ”), the typographic apostrophe (’) in new strings, the ellipsis character (…), the en dash in scores ("5–0") and in page titles, the minus sign (U+2212) for negative numbers. Never arrows (U+2192), check marks (U+2713) or "≤" (U+2264) in copy; they are outside the font subset. Phase 4 strings stay as they are.

## Screens and layout

Every screen uses the floodlit composition: the dark page ground, quiet chrome, one focal element, and one `h1`. Page `<title>` is "{page title} – The Next Klopp" (en dash); home's is "The Next Klopp".

### App bar (shell pages: home, tracks, track, chapter, What's new, not-found)

- 56 px tall (`h-14`), page padding as the grid, on the page ground with no border and no shadow.
- Left: the wordmark "The Next Klopp" as a link to `/` (Label at 375, Heading from 768 px, display family; Phase 4 `ShellBar` sizing). Dev build only, from 768 px: a neutral Badge "Drafts visible" after the wordmark.
- Right from 768 px: nav links "Tracks" and "What’s new" (Label, `standalone` links, 44 px tall targets, 16 px apart), then the Theme menu (icon-only, `aria-label="Theme"`, options "Match my system", "Light", "Dark"; `localStorage` `tnk:theme`, Phase 4).
- Below 768 px: one icon-only button "Menu" (`MoreIcon`, `aria-label="Menu"`, tooltip "Menu") opening a Base UI `Menu` with link items "Home", "Tracks", "What’s new", a separator, then the theme radio items. The bar fits at 320 px.
- The current page's nav link has `aria-current="page"`, weight 600 and a 2 px ink underline. Never accent.
- A skip link "Skip to content" is the first focusable element; it is visually hidden until focused, then shows at the top left on the raised surface with the focus ring, above the bar.
- Landmarks: `<header>`, `<nav aria-label="Main">`, `<main id="content">`.

### Home `/`

**Decided:** no pitch or picture on home. A pitch with nothing to teach would be decoration, which DESIGN.md section 1 bans; the next action is the focal point.

Order at every width (one column, left-aligned, at most 65ch wide; at 1440 it sits in columns 1-7 of the 12-column content grid with the rest left empty):

1. App bar.
2. `h1` (Display): the next lesson's title, from `nextAction()`.
3. Context line (Label, muted): "Next in the study order. {Track title}, part {letter}. About {n} min."
4. Summary (Body): the first concept's `summary` from `research/concept-map.json` (at most 30 words; trimmed by the selector at a sentence end).
5. Primary CTA: "Start: {lesson title}" (full width below 768 px, auto width above; wraps to at most 2 lines).
6. Secondary links row (Label, `standalone`, 24 px below the CTA): "Browse the tracks" and "What’s new", 16 px apart.

Spacing: app bar, then 32 px (48 px from 1024 px), `h1`, 16 px, summary, 24 px, CTA, 24 px, links. Bottom padding 64 px from 1024 px.

**Empty home** (no shipped lesson in this build; this is the Phase 5 production state, because fixtures never ship): `h1` "The first lesson is on its way", body "Track 0, Start here, ships first. The tracks page shows what is coming next.", primary CTA "Browse the tracks" (to `/tracks`), secondary link "What’s new". `nextAction()` returns `null` for this case and a unit test covers it.

### Tracks `/tracks`

- `h1` (Display) "Tracks". Context line (Label, muted): "{N} tracks, from the laws of the game to running a club. Lessons ship one chapter at a time." (`N` counted from the track list, never typed.)
- **Decided: two groups, not 29 identical badges.** Group 1 `h2` "Ready to study": tracks with at least one lesson in this build, in track-number order. Group 2 `h2` "Coming next": all other tracks, in track-number order, in muted ink. A group with no rows is not rendered. When group 1 is empty, one Body line under the context line reads "No track has a lesson in this build yet. Track 0, Start here, ships first."
- Each row (`ListRow`, an `<ol>` item, min height 44 px, 8 px vertical padding, 1 px `--control-border` rule between rows, no card, no box):
  - Ready row: the whole row is one link to `/tracks/:trackId`. Line 1: track title (Body 600). Line 2 (Label, muted): "Track {n}. {k} lessons ready." Hover: panel background; focus: the focus ring on the row.
  - Coming-next row: plain text, not focusable, not a link. Line 1: track title (Body 400, muted). Line 2 (Label, muted): "Track {n}".
- Track titles and numbers come from `TRACKS` in `scripts/research/lib/domains.ts` (moved or re-exported to a shared module the app can import; a test asserts every track id in `concept-map.json` has a title).
- Fixture build only (`VITE_INCLUDE_FIXTURES=1`): a third group `h2` "Test fixtures" lists the fixture lessons as lesson rows. Never in study or Vercel builds.
- Width: the list is at most 720 px wide at every width; 375 and 768 are one column.

### Track `/tracks/:trackId`

- Breadcrumb (Label, `<nav aria-label="Breadcrumb">`, `<ol>`): "Tracks" / "{Track title}" (current, not a link, `aria-current="page"`). The "/" separators are `aria-hidden`.
- `h1` (Display): track title. Context line (Label, muted): "Track {n}. {c} concepts in {p} parts."
- List of parts (chapters), `ListRow`: line 1 "Part {letter}" (Body 600); line 2 (Label, muted) "{k} lessons ready" as a link row, or a plain row with the neutral Badge "Coming next" when the part has no lesson in this build.
- **Coming-next track** (no lesson in this build, reached by URL): the parts list is replaced by a `StatusPanel` (no danger border): heading "This track is coming next", body "Its lessons are still being built. Lessons ship one chapter at a time, so check What’s new for each one.", links "Browse the tracks" (standalone) and "What’s new". No primary button.
- Unknown track id: the not-found layout with `h1` "No track called “{id}”" and body "This build has no track with that id. Pick one from the tracks list.", primary "Browse the tracks".

### Chapter `/tracks/:trackId/:chapterId`

- Breadcrumb: "Tracks" / "{Track title}" / "Part {letter}" (current).
- `h1` (Display): "{Track title}, part {letter}". Context line (Label, muted): "{k} lessons. About {m} min in total."
- Lesson rows in curriculum order, each one link to `/learn/:lessonId`: line 1 lesson title (Body 600); line 2 (Label, muted) "About {n} min". Badges on line 2, after the time, 8 px apart: the ink "New" Badge when the lesson appears in a What's new entry dated within the last 14 days of the build date; dev build only, the neutral status Badge (table under "Dev status badge").
- When the part's concept count is greater than its lesson count, one Label line (muted) closes the list: "More lessons in this part are coming next."
- Empty part reached by URL: `StatusPanel` heading "This part is coming next", body "No lesson in this part has shipped yet.", link "Back to {Track title}".
- Unknown chapter id: not-found layout, `h1` "No part called “{id}” in {Track title}", primary "Back to {Track title}".

**Chapter label decided:** the UI calls a chapter a "part" with its letter, because `concept-map.json` groups concepts by `part` (A, B, …) and has no chapter titles. If a later spec adds chapter titles, line 1 becomes "Part {letter}: {title}" additively.

### What’s new `/whats-new`

- `h1` (Display) "What’s new". Context line (Label, muted): "New lessons and changes, newest first."
- Entries from `content/whats-new.json`, newest first, each an `<article>` separated by a 1 px rule and 32 px of space:
  - Date (Label, muted, `<time datetime="YYYY-MM-DD">`): "28 November 2026" (day month year, no weekday).
  - Title `h2` (Heading).
  - Summary (Body, one line in the source, at most 30 words).
  - Lesson links (Label, `standalone`, one per line): the lesson title, to `/learn/:lessonId`. Lesson ids not in this build's manifest are left out; the entry itself stays.
- Empty (no entries): `StatusPanel` heading "Nothing new yet", body "When a lesson ships, it appears here with its date.", link "Browse the tracks".
- Seed entry for Phase 5 (so production is not empty): title "The app is ready for lessons", summary "Tracks, What’s new and the lesson player are in place. Track 0, Start here, is the first track to ship.", no lesson ids.

### Lesson runtime `/learn/:lessonId`

URL: `/learn/:lessonId?step=<stepId>` (deep link to a screen; unknown or missing `step` opens the first screen) and `&fallback=1` (opens every interaction in its text version; the walker's keyboard pass uses it). Moving between screens updates `step` with `replace`, so the browser's Back leaves the lesson and the in-app Back moves one screen.

**Regions** (DESIGN.md section 6 names): top bar, step rail, title, step, visual, controls, readout, legend, source, nav (holds the CTA).

- **Top bar:** `ShellBar` with the lesson time ("About {n} min") and the Theme menu. Phase 5 passes no focus switch and no "I'm confused here" (Phase 6 adds them; the props become optional, additively). The wordmark is a link to `/`.
- **Breadcrumb** (Label) above the title: "Tracks" / "{Track title}" / "Part {letter}". Fixture lessons show "Home" / "Test fixture".
- **Title:** `h1` (Display) lesson title; context line (Label, muted) "{Track title}, part {letter}". Dev build: the status Badge after the context line. Regulation template: the date line from the lesson's `<Rule>` sources sits under the context line (below).
- **Step rail:** `StepRail`, forms `{ base: "compact", md: "strip", xl: "vertical" }` (Phase 4). **Screen change behaviour** (Back, CTA or a deep link):
- The new screen replaces the old one at once. No slide, fade or scroll animation (decided: motion carries meaning and a screen swap carries none).
- The window scrolls to the top of `<main>` instantly; focus moves to the new step heading; a polite live region announces "{rail label}, screen {i} of {n}: {step heading}".
- No single-key shortcuts in Phase 5 (WCAG 2.1.4). Tab, Shift+Tab, Enter and Space do everything.
- Tab order follows visual order at every width: the walker's keyboard pass asserts that each newly focused element inside `<main>` is not above the previous one by more than 1 px, except when focus enters the 1440 reading column from the centre column.

- The title, rail and breadcrumb come from the eager lesson manifest and render at once. While the lesson's MDX chunk loads, the step region shows the status line "Loading the lesson…" (`role="status"`, `aria-busy` on the step). No spinner, no shimmer, no skeleton animation.
- MDX chunk fails (for example after a new deploy): `StatusPanel` with the 4 px `--danger` left border, heading "This lesson didn’t load", body "The lesson file couldn’t be fetched. Reload the page; if the app was just updated, a reload picks up the new version.", primary "Reload page".
- Unknown lesson id: not-found layout, `h1` "No lesson called “{id}”", body "This build has no lesson with that id. It may still be a draft, or the link has a typo.", primary "Browse the tracks".
- Unknown `step` id: the first screen opens and a Label status line under the breadcrumb says "No screen called “{step}” in this lesson, so it opens at the start." (polite, not an error colour).

**Lesson complete** (after "Finish lesson"; `data-lesson-complete` on the region, not a URL state, nothing stored):
- The rail shows all seven positions complete. The step region shows `h2` "Lesson finished" and the Body line "You finished “{lesson title}”."
- When a next lesson exists in the study order: primary "Start: {next lesson title}" and the standalone link "Back to {Track title}, part {letter}". Otherwise: primary "Browse the tracks".
- No score, no "great job", no confetti, no count of right answers.

### Interaction slot (`InteractionSlot`)

- A region `<div data-interaction="{registry id}" role="group" aria-labelledby="{step heading id}">`.
- Header row, right-aligned, above the interaction: the Switch "Text version", shown only when the registry entry's fallback is a different component from its main component. Checked = the fallback renders in place of the main component; state lives for this lesson visit only, `?fallback=1` forces it on. The switch is the first focusable element in the slot.
- Below the interaction: the readout or feedback region, which is also the polite live region for that interaction.
- Loading (lazy component): the frame keeps its height (a pitch holds its aspect ratio; list interactions reserve no height because they render with the step) and the status line reads "Loading the activity…".
- Error (the component throws or its data fails): `StatusPanel` with the danger border inside the slot, heading "This activity didn’t load", body "Reload the page. If it fails again, switch on Text version to carry on with the same task." The step CTA appears so the learner is never stuck.
- Dev only: unknown id renders "No interaction called “{id}” is registered. Add it to src/interactions/registry.ts or fix the id in lesson.json."; invalid props render "The settings for “{id}” don’t match its schema: {first issue}. Run npm run validate for the full list." Both are blocked from shipping by the validator.

**`quiz-choice`** (from a spec `quiz[]` item, props `{ itemId }`):
1. Question as the radio group's label (Body 600), then 2-4 `QuizOption` rows, 8 px apart, full width of the slot (at most 720 px).
2. Choosing an option gives it the selected look (accent marker, the radio's checked state). The primary button "Check answer" sits under the options.
3. "Check answer" with nothing chosen: inline error under the options in `--danger`, "Pick an answer first.", linked by `aria-describedby`; focus stays on the group.
4. After checking: the chosen option shows Correct (check icon + "Correct") or Not quite (cross icon + "Not quite — here is the answer"), the right option shows the Correct look, the others take the disabled look; "Check answer" is removed. A panel (`Surface` panel, radius 6 px, padding 16 / 24 px) shows the explanation (Body). The live region announces "Correct. {explanation}" or "Not quite — here is the answer. {right option}. {explanation}". Focus moves to the panel. The step CTA appears.
5. No retry and no score in Phase 5 (the review queue is Phase 6).

**`predict-then-reveal`** (props `{ question, options, answer, revealText, target? }`; spans a `predict` screen and the `reveal` screen after it):
1. Predict screen: the question and options as in `quiz-choice`; primary "Lock in my guess"; with nothing chosen, the inline error "Pick a guess first."
2. After locking in: the options lock (disabled look, the chosen one keeps its selected marker and gains the Label "Your guess"); the step CTA reads "See the answer". No right or wrong is shown yet.
3. Reveal screen: two rows in a panel, "Your guess: {option}" and "What happened: {answer}", then the reveal text (Body). On a pitch the answer marker draws in over `--duration-draw` (240 ms, instant under reduced motion), with no shake, bounce or confetti. When the guess matches, the row carries the check icon and "Correct"; otherwise the cross icon and "Not quite".
4. Reveal screen opened with no guess (deep link or reload): the panel shows "What happened: {answer}" and the Label line "You didn’t lock in a guess on the last screen." The guess lives in memory for the visit only.

**`order-sequence`** (props `{ prompt, items[], correctOrder[] }`, items shuffled with a seeded order so the start state is stable for tests and never already correct):
1. Prompt (Body 600), then an ordered list of items. Each item row: min height 44 px, `--control-border` 1 px border, radius 4 px, padding 8 / 16 px; contents in order: the drag handle (main version only, `aria-hidden`, pointer only), the item text (Body), then icon buttons Move up and Move down (44 × 44 px, `aria-label` "Move “{item}” up" / "… down", tooltip with the same name; Move up is disabled on the first item, Move down on the last).
2. Moving announces "{item} moved to position {k} of {n}." Focus stays on the button that moved it (it follows the item). In the main version the moved item slides over `--duration-ui` with `--ease-ui` using `transform` only; instant under reduced motion and in the fallback.
3. Primary "Check order" under the list.
4. After checking: each item shows the check icon and "Right place" or the cross icon and "Should be {k}"; the move buttons and handles are removed. When any item is wrong, a panel lists "The right order" as an ordered list. The live region announces "{r} of {n} in the right place." The step CTA appears.

### Claim components and source chips

Claim text is ordinary prose (ink, Body, no highlight, no underline: underlines mean links). What makes a claim visible as sourced is its chip.

**`SourceChip`** (`data-claim-meta`, so neither word counter counts it):
- An inline `<button>` placed right after the claim text, 4 px after the last word, `display: inline-flex` at the text baseline, inside the `<p>`.
- At least 24 × 24 px, padding 0 4 px, radius 2 px (`--radius-sm`), 1 px `--control-border` border, transparent fill, text Label 600 ink: the source number for this step ("1", "2", …), the same number as in the source line. One registry id cited twice in a step reuses its number.
- Accessible name: "Source {n}: {publisher}, {title}"; tooltip "Source: {publisher}"; `aria-haspopup="dialog"`, `aria-expanded`.
- States: rest; hover (panel fill); focus-visible (the focus ring); open (ink border, panel fill). Dev only: a registry id that does not resolve renders the chip text "Source missing" in `--danger` with a danger border (the validator blocks shipping, so production never shows it).

**`SourcePopover`** (Base UI Popover on the raised surface, radius 6 px, padding 16 px, at most 320 px wide, scale 0.98 to 1 with a fade over `--duration-ui`, instant under reduced motion; closes on Escape and outside click, focus returns to the chip):
1. Title (Body 600): the registry `title`.
2. Publisher (Label, muted).
3. A definition list (Label): "Type" (the registry `type` in words, for example "Regulation", "Article", "Dataset"); "Licence" (`license.name`, else "Not stated"); "Checked" (`as_of`, "27 November 2026"); for regulations also "Effective from" (`effective_date`, the new additive registry field); for data-bound `<Stat>`: "Data" ("{dataset} {version}, field {field}").
4. Standalone link "Open the source" to the registry `url`, new tab, accessible name "Open the source (opens in a new tab)".

**`<Fact source="reg-id">`**: inline claim text, then its chip.

**`<Stat>`** (`source="reg-id"` or `data="dataset/version/file#field"`, plus `value`, `unit`):
- `variant="inline"` (default): the value and unit in mono `tabular-nums` at Body size and weight 600 ("18.4 s"), the rest of the children as prose, then the chip. Negative values use U+2212.
- `variant="figure"`: renders through `StatCard` (Display mono figure, Label caption), with the chip after the caption.
- Data-bound loading: the value shows "…" (status); data missing or invalid: the value shows "—" and the popover's first row reads "Value unavailable: the data file didn’t load. Run npm run data, then reload this page." The chip still opens.

**`<Rule source="reg-id" law="…">`**: a block rule card, not inline:
- `Surface` panel, radius 6 px, padding 16 px at 375 and 24 px from 768 px; the rule paraphrase (Body); then the date line (Label, muted, `data-claim-meta`): "Effective from {effective_date} · As of {as_of}" (the DESIGN.md section 6 regulation date line, the one place a middle dot is used); then the chip and the standalone link "Read the official text" (new tab).
- When `as_of` is more than 12 months before the build date, a neutral Badge "Recheck due" sits on the date line. **Decided** as the on-screen flag DESIGN.md section 6 asks for when a rule may have changed after its as-of date.
- The validator fails a `<Rule>` whose source lacks `effective_date` or `as_of` (CONTEXT).
- In the `regulation` template the lesson's first `<Rule>` date line also appears under the title.

**`<Contested sides=[{claim, source}…]>`**: a block panel:
- `Surface` panel, radius 6 px, padding 16 / 24 px. First line: the neutral Badge "Contested", then the topic sentence (the children, Body).
- The sides as an unordered list, always stacked (the reading column is too narrow for columns), 1 px rule between sides, 16 px gap; each side is its claim (Body) and its own chip.
- At least 2 sides, each with a resolvable source (validator). The badge text is the label; colour is never the cue.

**`<Num kind="shirt|ordinal|formation|time-in-lesson|count-on-screen">`**: renders `<span data-num="{kind}">` with no visual change (Body, sans). It only tells the validator the number is allowed without a source.

**`<Step id>` and `<Visual>`**: `<Step>` renders the step region and passes `<Visual>` children to the visual region. Lesson files import nothing; every component comes through `MDXProvider`.

## Accessibility contract (checked by the walker and `review:screens`)

- One `h1` per page; headings descend one level at a time (`heading-order`). The lesson `h1` is the lesson title; each step heading is an `h2`; panels inside a step use `h3` only when they have a heading.
- Every page route change moves focus to the `h1` (`tabIndex={-1}`) and sets the document title; every screen change moves focus to the step `h2`.
- Every control has an accessible name (`control-names`); icon-only buttons have `aria-label` plus a tooltip with the same name.
- Feedback is icon plus words, never colour alone: "Correct", "Not quite — here is the answer", "Right place", "Should be {k}", the "Contested" badge.
- External links say they open a new tab in their accessible name.
- Live regions: one polite region for screen announcements; each interaction's readout region is polite. No assertive regions.
- Walker passes per lesson (QA-03): axe with WCAG 2.2 AA tags at every screen and in the complete view, zero violations; a keyboard-only pass with `?fallback=1`; a reduced-motion pass; the colour-contrast rule; and the performance budget recorded in DESIGN.md section 8 (exact per-lesson numbers come from 05-RESEARCH and are added there).
- `review:screens` must PASS on: `/`, `/tracks`, `/tracks/t00-start-here`, one chapter route, `/whats-new`, a not-found URL, and `/learn/fx-a-goal-in-ten-actions` with `--states step=<id>` for every step id, on the fixture preview build, at 375, 768 and 1440 in both themes.
