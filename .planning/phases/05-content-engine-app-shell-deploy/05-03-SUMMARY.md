# Phase 5 Plan 03: Content validator core and safety rules Summary

**`npm run validate` parses every lesson with the build's own MDX parser, counts step words with the one `countWords` that `review:screens` also uses, writes and drift-checks `content/lesson-manifest.json`, and blocks nine kinds of structural and code-safety breaks. Each break prints one plain line, and each rule has a failing fixture with its exact output. The check runs in pre-commit and in the required `test` CI job.**

## Performance

- **Duration:** about 22 min (2026-11-28, 18:58 to 19:20 local)
- **Tasks:** 2 (tracer, TDD)
- **Files:** 44 changed

## Accomplishments

- **One parse:** `parseLesson` calls `createProcessor({ remarkPlugins: [remarkFrontmatter] }).parse({ path, value })` on LF-normalised text. `walk`, `stringAttribute` and a structural `MdNode` view let rules read the tree without the mdast-util type packages.
- **Step extraction:** `extractSteps` reads each top-level `<Step>`'s id, line, first `##` heading and visible text. Text inside a paragraph joins with `""` and blocks join with `" "`. Code, inline code, image alt, ESM, expressions, attribute values and the `<Visual>` subtree are skipped. On the fixture lesson the steps count 15 to 31 words.
- **Shared word counter:** `countWords` now lives in `scripts/lib/words.ts`. `scripts/review/lib.ts` imports and re-exports it, and `review.test.ts` is unchanged.
- **Manifest:** `content/lesson-manifest.json` has `schemaVersion: 1`. Lessons are sorted by id, and each one carries id, title, status, fixture, dir, route, template, track, chapter and durationMin. Each step carries id, screen, stage, heading, line, words, interaction and dataRefs, and the lesson also lists its quiz answer keys. A plain run reports `manifest-stale` when the committed file differs.
- **Rules:** `mdx-parse`, `schema`, `step-parity` (only in the MDX, only in the spec, out of order), `step-heading`, `mdx-frontmatter`, `mdx-code` (import/export, flow and text expressions, expression and spread attributes; `<Contested sides>` is statically evaluated and passes only as an array literal of `{ claim, source }` string objects), `block-component`, `unknown-component`, `link-scheme`.
- **Wiring:** `.husky/pre-commit` now ends with `node scripts/validate-content.ts`. The ci.yml `test` job runs `npm run validate` after `npm ci`. No job was added and no GitHub expression is inside a `run:`.

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] Added rule `mdx-parse`**
- **Found during:** Task 1
- **Issue:** `createProcessor().parse()` throws on bad MDX (for example an unclosed `<Step>`), and a missing lesson.mdx left nothing to parse. Either case would crash the CLI with a stack trace instead of printing a plain line.
- **Fix:** `loadLesson` catches the error and keeps `{ line, reason }`. The line comes from the `(57:1-57:25)` place in the micromark reason, because the VFileMessage `line` field is unset. The new rule `mdx-parse` prints "lesson.mdx is not valid MDX: … Fix the markup on this line." or the missing-file message. It has fixture folder `content/_fixtures/invalid/mdx-parse/`.
- **Files modified:** scripts/lib/content/context.ts, scripts/lib/content/rules/structure.ts, scripts/lib/content/rules/index.ts (`ParseError`, `LessonInput.parseError`)
